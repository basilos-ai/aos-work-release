# 日常运维

以下命令均在 `/data/basil/` 执行。

## 查看状态

推荐使用部署脚本汇总查看三套 Compose 项目的容器状态、健康度和重启次数：

```bash
./deploy.sh --health
```

健康度显示“未配置”表示镜像没有声明 Docker healthcheck，此时仍需结合容器状态和日志判断。一次性初始化服务退出码为 `0` 属于正常状态。

也可以分别执行原始 Compose 命令：

```bash
docker compose --env-file .env.middleware ps
docker compose --env-file .env.middleware --env-file .env.studio \
  -f docker-compose.studio.yaml ps
docker compose --env-file .env.middleware --env-file .env.workbench \
  -f docker-compose.workbench.yaml ps
```

## 查看日志

```bash
# 共享中间件
docker compose --env-file .env.middleware logs --tail 200 -f postgresql redis rabbitmq minio

# Studio
docker compose --env-file .env.middleware --env-file .env.studio \
  -f docker-compose.studio.yaml logs --tail 200 -f studio studio-frontend

# Workbench
docker compose --env-file .env.middleware --env-file .env.workbench \
  -f docker-compose.workbench.yaml logs --tail 200 -f workbench workbench-runtime-node
```

中间件日志命令只保留实际由 Compose 部署的服务名。

## 重启并加载环境配置

运行 `sudo bash deploy.sh`，主菜单选 `7`，选择整套 Studio、Workbench 或单个服务。脚本使用 `up --force-recreate` 加载最新环境变量；单服务操作不重建依赖，整套操作按 Compose 依赖启动。镜像优先使用缓存；端口冲突时输入新端口，保存配置后自动重试。容器重建保留持久化挂载，不删除数据。

更换域名可直接选菜单 `8`，完成 DNS 检查、证书、环境变量和容器配置。环境和镜像问题选菜单 `9`；只检查文件及基础环境可运行 `sudo bash deploy.sh --check`。

## 启动与停止

直接运行 `./deploy.sh`，在主菜单选择“停止服务”，可停止 Studio、Workbench、全部应用服务或包含共享中间件的全部服务。脚本只停止容器，不删除容器、数据卷或环境文件。

启动顺序：共享中间件 → Studio → Workbench。中间件全部使用外部服务时，跳过第一条命令。

```bash
docker compose --env-file .env.middleware up -d --wait --wait-timeout 240
docker compose --env-file .env.middleware --env-file .env.studio \
  -f docker-compose.studio.yaml up -d --wait --wait-timeout 240
docker compose --env-file .env.middleware --env-file .env.workbench \
  -f docker-compose.workbench.yaml up -d --wait --wait-timeout 300
```

停止顺序相反：

```bash
docker compose --env-file .env.middleware --env-file .env.workbench \
  -f docker-compose.workbench.yaml stop
docker compose --env-file .env.middleware --env-file .env.studio \
  -f docker-compose.studio.yaml stop
docker compose --env-file .env.middleware stop
```

只停止某个应用时，不要停止共享中间件。

## 更新

使用脚本选择单个服务，输入该服务的 Docker tag；留空则沿用当前 `.env.*` 中的版本：

```bash
./deploy.sh --update
```

- 脚本先通过临时环境变量解析并拉取目标镜像。拉取失败时，不修改 `.env.*`，也不重建容器。
- 拉取成功后，脚本备份对应 `.env.*`，再写入新 tag。
- 只使用 `--no-deps --pull never --force-recreate` 重建所选服务，不连带重建依赖服务。
- 更新成功以 Compose `--wait` 和服务状态为准，不能只看镜像拉取成功。
- 更新失败时，脚本恢复环境文件备份并尝试重建原版本；如果自动恢复失败，立即检查容器和日志。
- 只能更新已经由当前 Compose 项目部署的服务；外部中间件不在脚本管理范围内。
- PostgreSQL、Redis、RabbitMQ 和 MinIO 默认不确认更新，必须先完成备份并确认跨版本兼容性。
- Runtime Sandbox 更新只拉取并记录新镜像，新建 Sandbox 使用新版本，已经运行的 Sandbox 不会被强制替换。

### Workbench 更新顺序

同一发布批次同时包含后端和前端时，按以下顺序更新：

1. 先拉取所有目标镜像；任一镜像拉取失败则停止。
2. 备份 `.env.workbench` 和数据库。
3. 更新 Workbench API，并检查迁移、健康状态和本机接口。
4. 后端验收通过后再更新 Workbench Frontend。
5. 检查前端入口、`/basilcraw/api/`、对象存储路径和最近的 `502` 日志。
6. Runtime 未在本次范围内时，核对其镜像和容器未变化。

Workbench API 的启动命令包含 `npm run migrate:up`。恢复旧镜像和 `.env.workbench` 不能撤销已经执行的数据库迁移，不得把镜像恢复描述为完整数据库回滚。

### Workbench Frontend 与 Nginx

前端镜像内的 Nginx 负责三类上游：

| 路径 | 上游 |
| --- | --- |
| `/basilcraw/api/` | Workbench API，即 `SERVER_HOST` |
| `/bascilclaw`、`/bascilclaw/` | 对象存储，即 `OBJECT_STORAGE_HOST` |
| `/basilos-subapp/`、`/oauth/`、`/basilos`、`/typekey` | 平台网关，即 `BASILOS_GATEWAY_HOST` |

`OBJECT_STORAGE_HOST` 是 Nginx 上游，不是 React 构建变量。当前前端镜像使用 Docker DNS 在请求阶段解析对象存储主机；MinIO 不可用时只应影响对象请求，前端首页仍应启动。若升级后前端容器因 `host not found in upstream` 无法启动，说明镜像仍包含旧版静态解析配置，应更换前端镜像，而不是在宿主机临时覆盖镜像内模板。

前端代理配置变化应通过新镜像发布。只有当前环境明确挂载了持久化 Nginx 配置时，才允许在备份、`nginx -t` 和明确回滚方案下热更新；不能假设单纯重启旧镜像会获得新配置。

### 更新后验证

```bash
./deploy.sh --health

docker compose --env-file .env.middleware --env-file .env.workbench \
  -f docker-compose.workbench.yaml logs --since 10m --tail 200 \
  workbench workbench-frontend
```

至少核对实际镜像、运行/健康状态、重启次数、持久化挂载、本机 HTTP、同源 API、对象存储路径和公网入口。未登录 API 返回 `401` 或 `403` 可作为路由可达证据；`502`、`000` 或超时均视为失败。

## 备份

本地部署时至少备份：

- PostgreSQL 的 `basilos` 数据库，包含默认 schema、Studio 的全部 `base{id}`、`workbench`、`runtime` 及迁移记录和扩展。
- MinIO 中 Studio 和 Workbench 使用的 Bucket。
- `workbench/storage/`（包括新用户模板 `workbench/storage/templates` 和 OIDC 签名密钥 `workbench/storage/oidc`）、`workbench/frontend-logs/` 和 `data/studio-logs/`。
- `.env.middleware`、`.env.studio`、`.env.workbench` 和对应 Compose 文件。

使用外部中间件时，按服务商的备份方案备份。Redis 和 RabbitMQ 不能代替 PostgreSQL 与对象存储备份。

环境文件更新时，`deploy.sh` 会生成 `.env.*.bak.update-*`。这些备份包含敏感信息，只能保存在受控主机上并沿用原文件权限，不得提交到 Git 或发送到聊天记录。

### 新用户模板与历史 App

部署包直接提供运行模板 `workbench/storage/templates/AGENTS.md`。修改运行模板 `workbench/storage/templates/AGENTS.md` 前先备份，采用同目录临时文件加原子重命名更新；不覆盖已有用户的指令文件。新部署不再播种内置 App，升级不得删除已有 `workbench/storage/resource-hub` 文件、数据库资源及安装记录。历史 App 的 OAuth 接入需单独配置，不属于默认部署流程。
