# 参考信息

## 服务与端口

| 分类 | 服务 | 默认端口 |
| --- | --- | ---: |
| 共享中间件 | PostgreSQL | 5432 |
| 共享中间件 | Redis | 6379 |
| 共享中间件 | RabbitMQ / 管理端 | 5672 / 15672 |
| 共享中间件 | MinIO API / Console | 9000 / 9001 |
| Studio | Frontend / API / Node Sandbox | 12000 / 12001 / 12002 |
| Workbench | Frontend / API / Runtime Gateway | 11007 / 11001 / 11002 |

Compose 使用 `宿主机端口:容器端口`，映射到所有宿主机接口。云安全组限制中间件、API、Runtime 和 Console 的访问来源；域名入口使用宿主机 Nginx 的 80/443。

## Docker 网络

| 网络 | 用途 |
| --- | --- |
| `basilos` | 由 `BASIL_NETWORK_NAME` 指定；连接共享中间件、Studio Frontend / API、Workbench Frontend / API 和 Runtime Node |
| Studio 内部网络 | 连接 Studio Frontend、Studio API 和 Node Sandbox |
| Workbench 内部网络 | 连接 Workbench Frontend、Workbench API 和 Runtime |

三个 Compose 项目都将 `basilos` 声明为外部网络。部署前创建一次，避免将网络绑定到某个应用 Compose 项目。

同机部署时，Workbench 的 `BASILOS_GATEWAY_HOST=http://studio-frontend/` 通过共享网络访问 Studio Frontend。两个 Frontend 都必须加入该网络；仅连接各自内部网络时，Workbench 前端 Nginx 无法解析 `studio-frontend`，会报 `host not found in upstream` 并反复重启。当前 Studio Compose 已包含此网络连接，已有部署更新配置后需应用到容器。

## 数据边界

| 数据 | 位置 |
| --- | --- |
| Studio 业务数据 | PostgreSQL `basilos` 数据库 |
| Workbench 业务数据 | PostgreSQL `basilos` 数据库的 `workbench` schema |
| Runtime 执行数据 | PostgreSQL `basilos` 数据库的 `runtime` schema |
| Studio 缓存 | Redis DB `0` |
| Workbench / Runtime 缓存 | Redis DB `1` |
| Studio 文件 | Studio 私有与公开 Bucket |
| Workbench 文件 | `bascilclaw` Bucket（Compose 默认）与 `workbench/storage/` |

共享中间件只复用实例和连接凭证，不合并 Studio、Workbench 和 Runtime 的业务数据。

## Workbench 目录权限

| 目录 | 默认权限合同 |
| --- | --- |
| `workbench/storage/user` | `0:10001`，目录模式 `2770` |
| `workbench/storage/sandbox/workspaces` | `0:10001`，目录模式 `2770` |
| `workbench/storage/resource-hub`、`workbench/storage/templates` | `0:10001`，目录模式 `0700` |
| `workbench/frontend-logs` | `0:0`，目录模式 `0750` |

`workbench-storage-init` 创建应用目录，直接校验 `workbench/storage/templates/AGENTS.md` 并设置权限，不复制模板；模板文件模式为 `0644`。`workbench/storage/oidc` 由应用按需创建并保存签名密钥。新部署的 Resource Hub 不再预置内置 App。

`check-workbench.sh` 负责校正 UID/GID 和 Docker Socket 配置。

## Workbench Frontend 代理边界

| 浏览器请求路径 | 容器内上游 | 配置来源 |
| --- | --- | --- |
| `/basilcraw/api/` | Workbench API | `SERVER_HOST`，默认 `http://workbench:3000` |
| `/bascilclaw`、`/bascilclaw/` | MinIO 或兼容对象存储 | `OBJECT_STORAGE_HOST`，默认由 `MINIO_HOST` 和 `MINIO_PORT` 组成 |
| `/basilos-subapp/`、`/oauth/`、`/basilos`、`/typekey` | BasilOS 平台网关 | `BASILOS_GATEWAY_HOST` |

对象存储上游使用 Docker 内置 DNS `127.0.0.11` 动态解析，并完整保留请求 URI 与查询参数，避免破坏预签名 URL。MinIO 暂时不可解析或不可连接时，只应影响 `/bascilclaw` 路由；如果整个 Workbench Frontend 容器无法启动，优先检查是否仍在运行旧镜像或旧 Nginx 配置。

`502 Bad Gateway` 表示前端 Nginx 已收到请求，但对应上游不可访问。排查时先按请求路径确定上游，再检查容器内 DNS、端口和目标服务状态，不能仅通过重启前端掩盖问题。

## 配置与版本依据

私有化交付按以下顺序确认真实配置：

1. 本目录的 Compose 文件与客户实际 `.env.*`。
2. `docker compose config` 展开的最终配置及运行容器的镜像、环境变量和挂载。
3. 对应版本镜像内的入口脚本与 Nginx 配置。

公司 Dev/Prod 的历史部署目录和当时使用的镜像 tag 仅可作为故障排查线索，不是客户私有化部署的默认值。私有化标准根目录为 `/data/basil`，每次交付必须使用发布清单中同一批次、已验证的镜像版本。
