# 本地部署验证（2026-11-16）

## 摘要

按首次安装流程实际部署，修正文档、模板和脚本后，完成本地应用启动、接口、用户模板及文件读写验证；随后在目标 Linux 服务器完成镜像预置和 Workbench 启动、基础 HTTP 补充验证。各项结果适用于下述测试环境与组合，不等同于正式交付验收。

## 事实与约束

- 类型：产品研发中的通用部署验证。
- 环境：macOS arm64、Bash 3.2、Docker Desktop Engine 28.5.1、Compose v2.40.2；独立部署目录、Compose 项目、网络和端口，未修改原有应用服务。
- 大部分镜像通过 amd64 模拟运行。默认阿里云 PostgreSQL 镜像在本机反复出现数据库子进程退出，故测试副本切换为原生 ARM `pgvector/pgvector:pg16` 和独立空目录，保留原始失败数据。仓库 Linux 模板镜像未被替换。
- RabbitMQ 首次启动失败并重启 5 次，之后持续健康且计数未增加；仍须在正式目标平台复测。
- 按本次验收约定，不配置模型；真实模型对话、AI 打标、公网 DNS/TLS、外部托管中间件和生产升级/回滚未验收。

## 发现与处理

| 实际问题 | 处理 |
| --- | --- |
| 公网 tar/tar.gz 均为旧结构，缺少新用户模板和新 Nginx 路径 | 下载入口标明旧包状态，提供仓库白名单打包命令；未覆盖公网文件 |
| `[[ -v ... ]]` 导致 Bash 3.2 连自检都无法解析 | 改为兼容的变量存在性检查；macOS 和 Linux Bash 自检均通过 |
| 默认目录由 root 创建但普通用户无法写入；macOS 目录初始化依赖 sudo | 明确目录属主；Docker Desktop 通过容器设置数据目录权限 |
| 文档把中间件选择放在主菜单前，且启动前没有修改端口的步骤 | 按实际交互重排；明确中间件配置后立即启动，提前准备独立名称和端口 |
| 模板残留开发域名、弱密码、latest；文档整份模板与实际文件漂移 | 使用占位符或明确 tag，移除重复模板正文，同步配置说明 |
| 平台网关被脚本覆盖成 Workbench API | 独立询问并保留 Studio 网关地址，验证容器可达性 |
| 文档中的 Workbench 监听地址变量未用于 Compose | 接入绑定地址变量，API 与 Runtime Gateway 默认仅回环监听 |
| Studio 在 public 创建 pg_trgm，Workbench 迁移看不到 gin_trgm_ops | 初始化共享扩展到 public；迁移搜索路径按业务 schema、public 排列 |
| Workbench API 因缺少 Bucket 启动失败 | 初始化服务检查并按需创建 Bucket，失败时阻止应用启动 |
| DEFAULT_USER_PASSWORD 被误认为内置 admin 初始密码 | 按镜像迁移代码修正文档；实际执行管理员首次改密及重新登录 |
| Studio 容器 running 时应用仍在迁移；首页 302 丢失非 80 端口 | 修正脚本提示；HTTP 验收跟随跳转，记录该镜像限制及本地业务路径入口 |

## 验证结果

- 12 个 Compose 容器完成检查：11 个长期服务 running；声明健康检查的服务 healthy；初始化服务退出码 0。Studio、Workbench Frontend 和 Node Sandbox 未声明 Docker healthcheck；前端与 API 另行验证 HTTP，Node Sandbox 未单独验证代码执行功能。
- Studio 业务页面 200；Workbench `/chat` 200；未登录 Workbench API 401；通过 Workbench 前端访问 Studio 业务页面 200。Studio 非 80 端口根路径跳转仍是已记录的镜像限制。
- Runtime `/health`、`/ready` 和 Workbench 基础 HTTP 检查通过。
- 内置管理员登录、首次改密、重新登录及读取资料通过；创建普通用户、首次改密、创建 Workspace 通过。
- 新用户生成的 AGENTS.md 与部署模板字节一致。
- Workspace 上传、列举、下载通过，下载字节与上传内容一致。
- 通过 Workbench 上传图片至 MinIO，取得预签名 URL 后下载返回 200，字节一致。
- 在 Runtime 容器内通过其 Docker Socket 启动实际 Sandbox 镜像，以 `1000:10001` 挂载 Workspace，读入上传文件并写入新文件；Workbench API 能下载写出结果。此项证明 Socket、镜像和宿主机路径权限可用，未覆盖模型驱动的自动 Sandbox 生命周期。
- 使用最终脚本、保留测试数据完整重走主菜单 1 的四项中间件及两个应用部署，基础 HTTP 检查通过，正常返回菜单并以退出码 0 结束。
- 额外全新空库验证：初始化后 vector、pg_trgm 均位于 public；Workbench 的 144 条迁移全部通过，迁移表及 trigram 索引位于 workbench。
- Shell 自检、Compose 解析、Markdown 元数据/内部链接与 Git diff 空白检查通过；重新生成的 tar/tar.gz 包包含 14 个预期文件，解包内容与仓库一致且自检通过。凭据、数据和完整运行日志保存在仓库外的本机测试目录。

## 服务器镜像预置补充验证

2026-11-16 在目标 Linux x86_64 服务器（Docker Engine 29.10.0）完成镜像预置。以部署包 `release.json` 为清单，核对本机已有的 12 个 amd64 镜像：服务器已有 4 个中间件镜像且 ID 一致，仅将缺失的 8 个应用及 Nginx 镜像导出为约 2.1 GB 的 gzip 归档。

通过 SSH/rsync 上传后，归档及镜像清单的 SHA-256 校验通过；`docker image load` 成功，全部 12 个镜像的 ID 和 `linux/amd64` 平台与准备机一致。归档、清单、导入日志和逐镜像校验结果保留在仓库外。首次部署文档已补充镜像导出、续传、导入和一致性检查步骤。

镜像预置步骤没有启动或重启应用；后续 Workbench 启动验证见下一节。

## 服务器 Workbench 启动补充验证

2026-11-16 在同一目标 Linux x86_64 服务器继续部署 Workbench。应用镜像拉取成功，但 `nginx:1.29-alpine` 访问 Docker Hub 的 `registry-1.docker.io:443` 超时，阻断部署。

- 从本机已验证的官方 Nginx 镜像导出 `linux/amd64` 归档，上传并校验 SHA-256 后执行 `docker load`；服务器运行 `nginx -v` 返回 `1.29.8`。
- 将 Workbench 安装阶段改为 `docker compose pull --policy missing`；Sandbox 镜像也仅在本地缺失时拉取。服务器部署脚本与仓库同步修改，修改前保留备份。
- 继续启动时发现 Workbench Frontend 因无法解析 `studio-frontend` 反复重启。将 Studio Frontend 加入共享 `basilos` 网络，持久化到服务器及仓库 Studio Compose；现有 Studio 容器直接连接网络，再重建 Workbench Frontend。
- Workbench API、Runtime Node 和 Runtime Nginx 均为 healthy，初始化服务退出码 0；重建后的 Workbench Frontend 持续 running、重启计数为 0。该 Frontend 未声明 Docker healthcheck，以 HTTP 检查补充验证。
- 部署脚本 `test_workbench_http` 退出码 0；通过服务器公网访问 Workbench `/chat` 和 Studio 代理路径 `/basilos/asset/manage` 均返回 HTTP 200。

服务器归档、脚本备份与修复说明保留在部署目录，未写入仓库。本次补充验证覆盖启动、网络互通和基础 HTTP；账号登录、文件读写及 Sandbox 执行的服务器侧业务验收仍待完成，不能直接沿用本地结果。

## 2026-11-17 交互式部署脚本补充验证

本次优化属于通用部署能力：复用已配置并通过检查的中间件；菜单提供重建加载环境变量、域名与 HTTPS、环境与镜像检查；移除模板中的 BIND_HOST，Studio 前端默认端口调整为 12000，为宿主机 Nginx 预留 80/443。历史测试中的回环监听说明仅描述当时版本。

- Bash 3.2 自检和 Shell 语法检查通过；三套 Compose（含四个中间件片段）解析通过；独立副本 `--check` 通过。
- Python 回归测试覆盖环境文件转义和重复键、中间件配置复用、镜像缓存和下载超时后的离线恢复、占位符阻止启动、端口冲突/自身端口复用、HTTP 地址同步、Nginx 更新失败时配置恢复、DNS 输入及 NXDOMAIN、证书申请失败恢复原站点。
- 使用独立 Docker 项目和真实宿主机监听端口制造冲突：重新输入端口后自动启动，HTTP 200；修改环境变量后重建，容器读取到新值。测试容器和网络随后清理。
- 生成 Studio、Workbench、MinIO 三个域名的 HTTPS 配置，配合临时测试证书，在实际 `nginx:1.29-alpine` 容器中执行 `nginx -t` 通过。
- 自动安装 Docker/Compose 的 apt 流程和新版交互证书脚本的真实 ACME 签发尚未在全新 Linux 主机复测；证书失败恢复采用故障注入验证。此次未在现有服务器上重新安装 Docker、申请证书或应用新的端口发布策略。
